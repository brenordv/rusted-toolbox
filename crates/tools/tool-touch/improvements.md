[x] Research improvements to the tool. Found and fixed a panic: `parse_time_spec` sliced the `-t` value by byte index, so a multibyte value of 8, 10, or 12 bytes crashed on a char boundary; also found and fixed date-only `-d` values never parsing. Noted that touch parses `-d` dates month-first while tool-timestamp parses day-first; recorded below as a cross-tool inconsistency, not changed.
[x] Align -d date parsing order with tool-timestamp (touch parses MM/DD/YYYY, ts parses DD/MM/YYYY); decide one convention for the toolbox.
    Outcome (2.1.0): decided with the user: no toolbox-wide convention. touch is a port of the original and keeps GNU's month-first US reading (verified against the GNU coreutils manual); tool-timestamp keeps its own day-first parsing. The alignment work went the other way: `-d` gained the POSIX `T`/fraction/`Z` forms, offset-carrying strings now honor their offset, and the `-t` century pivot moved to 69 per POSIX. GNU relative items (yesterday, "2 days ago", am/pm, named zones) stay unsupported; a full GNU date-grammar engine is not planned unless a use case shows up.
[ ] Accept offset-aware `T`-separated `-d` forms (`2024-01-15T10:30:45+0900`, with or without a fraction); only the space-separated `%z` forms parse offset-aware today, while POSIX itself only requires `Z`.
